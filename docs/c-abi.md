# C ABI (`bindings/ffi`)

The commands of the CLI (`docs/cli.md`) in process: one function takes a JSON request and gives the JSON
the CLI would print. Same dispatch (`bindings/cli/src/lib.rs`), same flags, same outcomes, same TLS verification;
nothing is reimplemented. Why this route and not one wrapper per language: `docs/adr/0001-c-abi-over-cli-wrappers.md`.

Artifacts of a build: `sunat_sdk_ffi.dll` / `libsunat_sdk_ffi.so` / `libsunat_sdk_ffi.dylib` (cdylib),
`libsunat_sdk_ffi.a` / `sunat_sdk_ffi.lib` (staticlib) and `bindings/ffi/include/sunat_sdk.h` (generated by
`bindings/ffi/scripts/header.sh`; CI fails if it is stale).

## Functions

| Function | What it does |
|---|---|
| `int32 sunat_sdk_call(const char *request, char **response)` | Runs one command. Always stores a response when `response` is not null |
| `void sunat_sdk_free(char *response)` | Releases a response. Null is ignored |
| `size_t sunat_sdk_response_len(const char *response)` | Bytes of a response, without the NUL |
| `int32 sunat_sdk_response_copy(const char *response, char *buffer, size_t capacity)` | Copies a response into the caller's buffer (for VB6, Visual FoxPro, PowerBuilder, which cannot read a pointer) |
| `const char *sunat_sdk_version(void)` | The SDK version; static, never released |
| `uint32 sunat_sdk_abi_version(void)` | `1`; a wrapper refuses a library with another value |

## Request and response

`request` is NUL-terminated UTF-8 JSON: `{"command": "sign", "flags": {"cert": "...", "key": "..."}, "input": {...}}`.

- `command`: any of the CLI's (`build`, `sign`, `zip`, `cdr`, `send`, `summary`, `ticket`, `status`, `validity`,
  `gre-send`, `gre-ticket`).
- `flags`: optional object; `"timeout": 30` is `--timeout 30`. Names and rules are the CLI's, an unknown flag is the same
  error. Values are strings or whole numbers.
- `input`: what the CLI reads on stdin, as a JSON value (`build`'s document, `sign`'s `{"xml"}`...). It reaches the command
  as the text the caller wrote.
- **The environment is not read.** `SUNAT_*` variables do nothing here: a host process shares its environment with
  everything it loads, so every value (endpoint, SOL user and password, certificate paths) comes in `flags`.

Status: `0` (`SUNAT_SDK_OK`) the response is the CLI's stdout; `1` (`SUNAT_SDK_ERROR`) it is `{"error": "<message>"}`, the CLI's
stderr with exit code 1; `2` the `response` pointer was null, nothing ran. A malformed request, a null request, invalid UTF-8
and a panic inside the library are status `1` with that shape; none crosses the ABI. `no_verdict`, `api_error` and the other
outcomes that the CLI prints with exit 0 are status `0`, exactly as there.

## Memory

- The response is allocated by the library and owned by it until `sunat_sdk_free`, called once, from any thread.
  Never `free()` it, never release it with the host's allocator.
- A caller that cannot read a pointer: `sunat_sdk_response_len`, a buffer of that length plus one, `sunat_sdk_response_copy`
  (`3`, nothing written, if the buffer is shorter than the length), then `sunat_sdk_free`.
- The request is only read during the call; the caller keeps it. Strings are UTF-8, not the code page of the host:
  VB6, Visual FoxPro and PowerBuilder convert their text to UTF-8 bytes first (an `ñ` in Latin-1 is rejected with
  `request is not UTF-8`, never misread).
- Secrets (SOL password, client secret) are in the request memory the caller owns; clear it after the call. They are never
  in a response or an error.

## Threads and time

No state between calls, no globals: any thread, concurrently (`concurrent_calls_share_nothing`). A call blocks until the command
ends; network commands are bounded by their `timeout` flag (default 90 s, as in the CLI), so a UI thread should not call
`send`. The library creates no threads of its own and installs no signal handlers.

## Windows and 32 bits

Functions are `extern "system"`: `__stdcall` on 32-bit Windows, the default of `Declare` in VB6, Visual FoxPro and
`FUNCTION ... LIBRARY` in PowerBuilder; the C convention elsewhere. The header spells it `SUNAT_SDK_CALL`. The exported names
carry no `_name@8` decoration, so `Declare Function sunat_sdk_call Lib "sunat_sdk_ffi.dll"` needs no `Alias`.
The DLL links the C runtime statically: it loads on a machine without the Visual C++ redistributable. VB6, Visual FoxPro and
PowerBuilder 32-bit load the `i686-pc-windows-msvc` build; PowerBuilder 64-bit and any 64-bit host load `x86_64`. A process
loads only the DLL of its own bitness.

## Checked in CI (`.github/workflows/ffi.yml`)

On Linux x86_64 and aarch64, macOS arm64 and x86_64, Windows x86_64 and i686: the 38 vectors through the ABI from Rust
(`bindings/ffi/tests/abi.rs`) and from C, shared and static (`tests/c/vectors.c`); on Windows the C test loads the DLL by name
under `/RTC1` (a wrong calling convention stops it) and the same battery runs from .NET Framework by P/Invoke, in the 32-bit
PowerShell for i686 (`tests/dotnet.ps1`). The header is regenerated and compared, and compiled as C and C++.
